## 1. Environment / Prerequisites

- Windows PC with the official Tailscale Windows client installed and signed into the same tailnet as the paired parent device — same connectivity prerequisite as `docs/detailed-spec.md` §7, extended to the PC's OS.
- Minimum Windows version: Windows 10 or later (confirmed constraint).
- Distribution: a single portable executable, not a Windows installer package (no MSI, no setup wizard) — the operator runs the `.exe` directly. Exact build mechanism (e.g. .NET single-file publish) is left to the eventual PLAN.md; this section fixes only the product-level requirement.

## 2. Role & Scope Relative to the Existing App

- Plays the same role as the Android child app (`docs/detailed-spec.md`, all sections describing the child/viewer side): screen viewing, tap/swipe input, text input, against an already-paired parent device.
- Does not change parent-side screen capture, encoding, background-kill mitigation, wake-lock behavior, or any other parent-side behavior described in `docs/detailed-spec.md` §2, §5, §6, §7, §8, §9, §11, §12 — all of that continues exactly as specified there, unaware of which kind of client (Android child or PC) it is talking to.
- The parent-side (Android) changes introduced by this feature are the manual pairing code addition (§3 below) and the `ParentAccessibilityService` addition for physical key relay (§11 below) — no other parent-side change.
- Application model: the PC client runs as an ordinary visible desktop window, like any normal Windows application — it does not minimize to the system tray, run as a background/headless service, or auto-start on boot. Closing the window ends the app normally, the same as a typical desktop application. See §8 for how this interacts with connection-state handling.
- **Single-instance enforcement (required)**: the PC client enforces single-instance operation (e.g. via a named mutex) — launching the `.exe` a second time while an instance is already running does not start a second, independent instance. Exact behavior on a second-launch attempt (e.g. bring the existing window to the foreground vs. show a message and exit) is left to the eventual PLAN.md; the requirement fixed here is only that a second instance must not run concurrently. Rationale: prevents two instances from racing to use the same pairing entry's shared secret against the parent simultaneously.

## 3. Pairing: Manual Code Addition on the Parent (Android) Side

- The existing QR-code pairing screen (`docs/detailed-spec.md` §13 step 4; the exact screen is `ParentPairingActivity`, see `docs/plans/pairing-and-onboarding/PLAN.md` §3-4) is extended to also render, alongside (not replacing) the existing QR code, **two additional pieces of information**: the Tailscale host address (IP/hostname, `parentHost`) as plain readable text, and a **separate, new, PC-pairing-specific manual code** — not a re-encoding of the QR's own `tempToken`. Three things are shown together on this screen: the QR code, the plain-text host address, and the manual code. Both additions are generated/rendered specifically to make the PC pairing case possible without a camera; the existing QR-only Android-to-Android pairing flow (`docs/plans/pairing-and-onboarding/PLAN.md` §4) is otherwise unchanged and keeps its own `tempToken` exactly as-is.
- **Why the host address must also be shown**: the manual code alone authenticates the handshake (it plays the same role the QR's `tempToken` does) but never tells the PC client *where* to connect — the QR encodes `parentHost` for the Android child automatically, but a PC operator typing a code by hand has no equivalent unless the host address is also shown as readable text.
- **Manual code alphabet**: Crockford Base32-style — digits `0`-`9` and uppercase letters `A`-`Z`, **excluding `I`, `L`, `O`, `U`** (Crockford's Base32 alphabet convention, a well-established standard specifically designed to avoid character-confusion ambiguity; a superset of the project's earlier ad-hoc `0`/`O`, `1`/`I`/`l` exclusion list). 8 characters, roughly 40 bits of entropy. Same validity window as the existing pairing listener (5 minutes, `docs/plans/pairing-and-onboarding/PLAN.md` §4 step 1) — the manual code is scoped to the same temporary pairing-listener session, not a separately-lived credential.
- **Case-insensitive entry, with full Crockford alias correction**: the PC client normalizes typed input before transmitting it as part of the handshake, using the standard, complete Crockford Base32 decode-normalization behavior (not a partial/ad-hoc subset) — the operator does not need to worry about matching the parent screen's exact letter casing. Normalization does two things: (1) uppercases the input, and (2) applies Crockford's standard alias-correction mapping — a typed `I` or `L` is treated as `1`, and a typed `O` is treated as `0` — before matching. This is chosen specifically because it absorbs plausible human mis-typing of visually-similar excluded characters without weakening the code's actual entropy: the excluded letters (`I`, `L`, `O`, `U`) were excluded from the alphabet specifically because of this visual-confusion risk, so correcting them on entry is the intended complementary behavior, not a security compromise. The parent-side comparison itself remains a simple exact-string match against its own (always-uppercase) generated code; all normalization happens client-side, not as new parent-side matching logic.
- **PC-side manual pairing screen has two input fields**, not one: the host address (IP/hostname) and the 8-character manual code — both must be entered, mirroring the two pieces of information now shown together on the parent's pairing screen (see above). See `docs/pc-client-spec.md` §6.
- **Attempt-rate limiting (required)**: because a human-typable 8-character code is necessarily much lower-entropy than the QR flow's own `tempToken` (which has no typability constraint), the parent-side temporary pairing listener (`docs/plans/pairing-and-onboarding/PLAN.md` §4) must enforce an attempt-count lockout specifically for manual-code submissions: after a small, bounded number of failed match attempts within the 5-minute window, further attempts are locked out for the remainder of that window. The exact threshold (e.g. 3, 5 attempts) is left open for the eventual PLAN.md to pick — not a product-level decision, only the requirement that a bounded lockout must exist is specified here. See `docs/DECISIONS.md` for the rationale (entropy + rate-limiting combined, rather than entropy alone). The manual code and the QR's `tempToken` share the same temporary listener/window but are tracked with **separate, independent failed-attempt counters** — a failed manual-code attempt does not count against the QR/`tempToken` lockout, and vice versa. This avoids one authentication channel's legitimate retry attempts (e.g. a few QR scan failures) from spuriously locking out an unrelated attempt via the other channel (e.g. someone then trying the manual code); the security difference between shared and independent counters is negligible given the already-small practical attack surface (same-tailnet-only, 5-minute window, `docs/spec.md` §7's minimal-security family-only posture).
- Exact text rendering of the manual code and host address (e.g. grouped in dashes for readability) is left open for the eventual PLAN.md — an implementation/display detail with no product-facing consequence, since the underlying values are what's authoritative.
- This is one of the two Android-side changes this feature requires (the other being the `ParentAccessibilityService` addition for physical key relay, §11) — see §2 above; the handshake sequence itself (child/PC dials `parentHost:PAIRING_PORT`, sends `PAIRING_HELLO`, receives `PAIRING_ACK`) is unchanged from `docs/plans/pairing-and-onboarding/PLAN.md` §4 steps 3-5 — the PC client performs the same steps the Android `ChildPairingScanActivity` performs today, just starting from an operator-typed host address and code instead of a scanned QR, and authenticating that typed code against the manual-code value (not the QR's `tempToken`) during the handshake.

## 4. PC-Side Pairing Data Model

- The PC client needs its own local pairing-entry-list concept, mirroring `docs/detailed-spec.md` §3's `PairingEntry` model (device/host address, shared secret, a child-assigned free-form label, creation time) — this is confirmed as needed (not an open question): the PC client must be able to store more than one paired parent, exactly as the Android child app does, per the same list-based-pairing rationale (`docs/spec.md` §5). The host-address field is populated from the operator's manual entry (§3's two-field pairing screen — host address plus code), rather than auto-discovered from a QR payload as on the Android child.
- This is a separate, PC-local list, independent of the Android child app's own list. If the same parent device is paired to both an Android child and this PC client, two independent pairing entries exist (one per client device, each with its own shared secret) — consistent with the existing "list of pairs, not fixed 1:1" model (`docs/spec.md` §5, `docs/detailed-spec.md` §3).
- The label remains purely client-side bookkeeping, same as `docs/detailed-spec.md` §3 — the parent device has no knowledge of it, on either client type.
- Storage mechanism (local file, Windows registry, etc.) is left open for the eventual PLAN.md — an implementation detail, not a product-level decision.

## 5. Video Transport & Decode

- The parent's Android app is unchanged: it continues to capture/encode via `MediaCodec` and send H.264 (Annex-B, in-band SPS/PPS) `VIDEO_FRAME` messages exactly as it does today for the Android child, per `docs/detailed-spec.md` §5 and the wire format already defined in `docs/plans/README.md` §4 (`net` package Message Protocol).
- The PC client decodes this same H.264 stream itself via **Windows Media Foundation** — the OS's own built-in, hardware-accelerated H.264 decoder — rather than a third-party library (FFmpeg was considered and rejected; see `docs/DECISIONS.md`). Exact API surface is left to the eventual PLAN.md (e.g. an `IMFSourceReader`/custom `IMFByteStream` fed by the incoming Annex-B NAL units, or a Media Foundation Transform (MFT) for H.264 decode driven directly) — a detail-level implementation choice, not a scope-level one; the requirement fixed here is only "Media Foundation, not FFmpeg or another third-party decoder."
- No new parent-side capture/encode path, no wire-protocol change — this section is purely about how the PC client decodes the already-existing stream.
- See `docs/DECISIONS.md` for the three-option comparison (reuse existing H.264 stream vs. a parent-side JPEG screenshot burst vs. a parent-side differential/dirty-rectangle screen-diffing codec) and why the H.264-reuse approach was chosen, and for the separate Media-Foundation-vs-FFmpeg decode-library comparison.
- Aspect-ratio handling (letterbox/pillarbox, never stretch) and rotation-driven dimension changes follow the same behavior already specified in `docs/detailed-spec.md` §12 and §15 — the PC client's rendering surface must reflow the same way the Android child's does, using the same frame-dimension header fields already defined in the wire protocol.
- **PC window size is independent of parent-side rotation**: the PC client's own window size is entirely under the operator's control (an ordinary resizable desktop window, §2) and is **not** automatically resized in response to a parent-side rotation event. Only the internal rendered-video-content area reflows/re-letterboxes within whatever window size the operator currently has at the time — the same way a standard video-player application (e.g. VLC) behaves when its source content's aspect ratio changes mid-playback. Minimum window size is left to the eventual PLAN.md as an ordinary implementation detail.
- **Low-latency decode configuration (required)**: the Media Foundation-based decode implementation must be configured for low-latency operation (e.g. `CODECAPI_AVLowLatencyMode` or equivalent MFT configuration) rather than the decoder's default buffering behavior. The default can introduce multi-frame (potentially 1-2 second) latency, which would defeat the purpose of real-time remote assistance during a live phone call. This is a firm product-level performance requirement, not merely an implementation detail — the exact API call sequence to achieve it remains a PLAN.md-level choice, but low-latency operation itself is not optional.
- **No pause/resume on minimize or occlusion**: the PC client applies no special pause/resume logic when its window is minimized or hidden behind other windows — H.264 decoding continues normally regardless of window visibility state. See `docs/DECISIONS.md` for why this deliberate simplicity choice was made over pausing decode while not visible.
- `FLAG_SECURE` black-screen help hint: mirrors the Android child's hint (`docs/detailed-spec.md` §5 — a black frame may mean a protected app such as banking or a password manager is open on the parent's device, not a connection problem) — same informational content, but the interaction is adapted to desktop conventions: a small info icon near the video view, revealed via a hover tooltip rather than Android's tap-to-open-dialog (mouse-driven rather than touch-driven UI). Exact icon/placement/wording is left to the eventual PLAN.md, the same as the Android version already leaves to `docs/plans/remote-input-control/PLAN.md` §9.

## 6. Session Establishment & Connectivity

- **Pairing-entry selection flow on launch**: mirrors the Android child's existing behavior exactly (`docs/detailed-spec.md` §3/§17) — no PC-specific deviation. If zero pairing entries exist, launch goes directly to the two-field manual-pairing screen (§3). If exactly one entry exists, it is auto-selected and no list is shown. If more than one entry exists, a selection list is shown first, and the operator picks one.
- Same parent-initiated connection model as `docs/detailed-spec.md` §17 / `docs/DECISIONS.md` #12: the parent dials the PC client, not the reverse. The PC client, once a pairing entry is selected (per the flow above), enters a "waiting for parent" state and listens for the parent's incoming session connection — same role the Android child's listener plays.
- Same `SESSION_HELLO` handshake and shared-secret validation as the existing protocol (`docs/plans/README.md` §4) — the PC client is, from the parent's perspective, indistinguishable from any other paired child device.
- Same Tailscale-based connectivity as `docs/detailed-spec.md` §7, using the Windows Tailscale client instead of the Android one.
- **Exclusive single-session model**: per `docs/detailed-spec.md` §17 / `docs/DECISIONS.md` #24, at most one client (Android child or PC client, any type) may hold an active `Live` session with a given parent device at a time — this is a core-app-level rule, not a PC-specific one. The PC client is simply one more client type subject to it: if the parent is already in a `Live` session with another client (an Android child, or another PC client instance elsewhere) when this PC client attempts to connect, that attempt is rejected or queued rather than accepted as a second concurrent peer. No PC-specific behavior is needed beyond following this same rule — the exact rejection/queue mechanism and its client-side UX are implementation details tracked as a follow-up to the already-merged `docs/plans/screen-sharing-core/PLAN.md` and `docs/plans/connection-status-and-resilience/PLAN.md` in GitHub issue [#9](https://github.com/hachi921082-source/Parent-Android-Remote-Control/issues/9).

## 7. Input Relay (Tap/Swipe/Text)

- Reuses the same wire messages already defined for the Android child: `INPUT_TAP`, `INPUT_SWIPE`, `INPUT_TEXT` (`docs/plans/README.md` §4) — no new message types.
- On the PC, these are sourced from mouse click (tap), mouse drag (swipe), and a text-entry box (text) instead of touch gestures — same underlying coordinate-scaling requirement as `docs/detailed-spec.md` §15 (coordinates calculated relative to the rendered video content area only, discarded rather than clamped when outside it) and the same tap-position visualization behavior as `docs/detailed-spec.md` §10 (local-only marker, 300ms fade, never confirmed via network round-trip).
- Text input follows the same mechanism/constraints as `docs/detailed-spec.md` §16: sent as a complete string on submit, not streamed per-keystroke; clipboard is never touched.
- View-only mode (input disabled while the parent's Accessibility Service permission is unavailable) follows the same `ACCESSIBILITY_STATUS` message and same all-input-disabled scope as `docs/detailed-spec.md` §11 — no new logic, same wire message drives the same behavior on this client too.
- **Tap-marker rendering coordinate space**: the local-only tap/swipe marker (`docs/detailed-spec.md` §10, reused as-is per above) is drawn at the actual on-screen position where the operator clicked, within whatever is currently rendered — i.e. already accounting for the current zoom level (§10) and any letterbox/pillarbox offsets, not tracked back into unzoomed, frame-relative coordinates. This follows directly from the existing "local overlay using the coordinates the child's device just sent" principle; nothing new is introduced, this only makes the zoom interaction explicit.

## 8. Connection-State-Driven UI

- Reuses the same connection-state model and timing thresholds already defined for the Android child: Idle/WaitingForParent (untimed, `docs/detailed-spec.md` §17) → Live → Reconnecting (≤60s, `docs/detailed-spec.md` §14) → Disconnected — no new states, no different timing for this client.
- Missed-heartbeat detection (~15s, 3 missed heartbeats) and the resulting Reconnecting/Disconnected UI states follow `docs/detailed-spec.md` §14 exactly, using the same `STATUS_HEARTBEAT`/`STATUS_EVENT` messages (`docs/detailed-spec.md` §9) already sent by the parent — no new wire-protocol content is added for this client.
- **Parent screen-sleep is not a PC-specific scenario**: when the parent's device screen goes to sleep, video frames simply stop arriving, and the same ~15s missed-heartbeat threshold above drives the transition to `Reconnecting` exactly as it would for any other frame-stoppage cause. This is identical to the already-merged Android child's behavior — no distinct "parent may be asleep" indicator or detection logic is added for this client.
- **Post-`Disconnected` destination**: matching the Android child's existing behavior (`docs/detailed-spec.md` §14 — "directs the child back to the idle/waiting screen... would need to explicitly restart the connect flow"), the PC client's `Disconnected` state returns to the pairing-selection/idle screen, not an automatic silent retry back into `WaitingForParent`. The operator must explicitly restart the connection (re-select the pairing entry, per §6's selection flow), the same as a fresh connection attempt.
- Parent device status display: the PC client displays the same status fields the Android child does (`docs/detailed-spec.md` §9) — Wi-Fi connected/disconnected, network type (Wi-Fi vs. mobile), signal strength where available, and SSID where available — sourced from the same `STATUS_HEARTBEAT`/`STATUS_EVENT` messages already used for the missed-heartbeat detection above (no new wire message). Exact panel/placement within the PC UI is left to the eventual PLAN.md; this section fixes only that the same content is shown, not the layout.
- Same no-special-affordance behavior after a parent-side process-kill as `docs/detailed-spec.md` §6 / `docs/DECISIONS.md` #13 — the PC client has no more visibility into the cause of a disconnect than the Android child does, and no distinct "resume" UI is built for it.
- Consistent with §2's "ordinary window, no tray/background" application model: closing the PC client's window at any point (regardless of `ConnectionState`) simply ends the session and the app, the same as closing any other desktop application — there is no "minimize to tray and keep the session alive in the background" behavior to design for.

## 9. UI Localization

- **Resolved**: the PC client's UI follows the same policy as the Android app (`docs/detailed-spec.md` §18, `docs/DECISIONS.md` #14) — Japanese, English, and Chinese (ja/en/zh), selected automatically from the OS locale, English fallback for any other locale, no in-app manual language picker. See `docs/QA.md` ("PC Viewer Client: Does the ja/en/zh UI-Language Policy Apply to Its UI Too?", RESOLVED) for the resolution record.
- Implementation vehicle: WPF's standard resource-localization mechanism (`.resx` satellite resource files per culture, e.g. `Strings.ja.resx`, `Strings.zh.resx`, default `Strings.resx` authored in English as the fallback), selected automatically via `CultureInfo.CurrentUICulture` at runtime — the Windows-side equivalent of the Android app's `values-ja/`/`values-zh/`/default `values/` resource-qualifier mechanism. This is a detail-level implementation note, not a full implementation plan; exact resource-file structure/build wiring is left to the eventual PLAN.md.

## 10. Zoom/Magnifier Display

- Purpose: help the operator precisely tap small UI elements on the parent's screen, leveraging the PC's larger display compared to a phone-to-phone view (`docs/pc-client-spec.md` §3).
- Trigger: the operator zooms into a sub-region of the rendered video content area (`RenderedContentRect`, `docs/detailed-spec.md` §15 / `docs/plans/README.md` §6) — exact UX (e.g. scroll-wheel zoom, or a dedicated zoom-toggle plus click-to-zoom-in) is left to the eventual PLAN.md; this section fixes only the required behavior, not the exact interaction.
- **Maximum zoom is capped to fit the current window — no pan/scroll, dynamically re-clamped on resize**: the maximum zoom level is always computed so the zoomed content fits entirely within the current window's rendering area; the operator can never zoom to a level where part of the content would be scrolled off-screen. This rule is continuously re-evaluated as the window is resized, not just at the moment zoom is applied: if the operator shrinks the window while zoomed in, the effective zoom level automatically reduces to keep the content fully visible within the new (smaller) window size — the same way a standard "fit to window" image/video viewer continuously recomputes its fit on resize. The window itself is never prevented from being resized smaller (consistent with §2's "ordinary, freely resizable window" principle) — only the zoom factor adapts to it. To zoom in further, the operator resizes or maximizes the window itself, unlike the parent's fixed physical phone screen. Because the entire zoomed content is always fully visible, there is no pan/scroll mechanism to design, and therefore no conflict between "panning around while zoomed" and the swipe-input drag gesture: mouse-drag while zoomed unambiguously means "send a swipe," exactly as when not zoomed.
- Coordinate scaling while zoomed: a tap/click made while zoomed-in still goes through the same coordinate-scaling pipeline already defined in `docs/detailed-spec.md` §15 (rendered-content-area fraction → parent-frame-resolution mapping) — computed against the zoomed sub-region's own mapping instead of the full frame's. The zoom is a display/input-mapping transform layered on top of the existing letterbox/coordinate-scaling logic (`docs/plans/remote-input-control/PLAN.md` §3-4) — it does not replace or bypass that pipeline, it feeds it a different (zoomed) content rect.
- Wire protocol: none — no new message type. The PC client still sends ordinary `INPUT_TAP`/`INPUT_SWIPE` messages (`docs/plans/README.md` §4) with correctly-scaled parent-frame coordinates, exactly as when not zoomed. The parent has no way to know, and does not need to know, whether a given tap came from a zoomed view — this is a purely PC-client-side (WPF) feature.
- No Android-side change required for this feature. See `docs/DECISIONS.md` for why this was confirmed feasible with zero wire-protocol/parent-side changes.

## 11. Physical Key Relay

- Purpose: beyond the existing complete-text-then-send `INPUT_TEXT` mechanism (`docs/detailed-spec.md` §16, unchanged, still used for typing full text), give the PC operator finer live control by relaying individual key presses as they occur on the PC keyboard.
- New wire message: `INPUT_KEY`, child→parent, carrying a key identifier from a fixed set. Scoped to navigation/editing keys only (not general keyboard passthrough): **Arrow Up/Down/Left/Right, Backspace, Delete, Enter, Tab, Escape**. This set was chosen as the minimal set covering live cursor/editing control that complements (rather than duplicates) the existing batch `INPUT_TEXT` flow — broader/general key passthrough was not requested and is not specified here. This message is added to `docs/plans/README.md`'s Message Protocol table (existing `net` package, alongside `INPUT_TAP`/`INPUT_SWIPE`/`INPUT_TEXT`) when a PLAN.md is eventually written for this feature — not modified there yet, per this project's convention of not editing `docs/plans/README.md` at the pre-PLAN.md specification stage.
- **Escape key mapping (distinct from the other five keys)**: Escape maps to Android's system-wide "Back" action — `AccessibilityService.performGlobalAction(GLOBAL_ACTION_BACK)` — rather than any text-field editing action. This is a deliberate, confirmed choice: unlike the other five keys (arrows, Backspace, Delete, Enter, Tab), which all have a meaning within a focused text field, Escape has no such meaning on Android — its closest and most useful analog is the system Back navigation gesture. Because `performGlobalAction` is a direct, always-available API call (not scoped to a focused editable node), Escape/Back is **not** subject to the injection constraint described below — it needs no node/selection-based workaround.
- **Android-side change (explicitly accepted exception)**: unlike the rest of this PC-client feature, which requires zero Android-side changes, this feature requires a small addition to the already-merged Remote Input Control tier's `ParentAccessibilityService` (`app/src/main/java/com/familyremote/app/parent/ParentAccessibilityService.kt`) to receive `INPUT_KEY` and inject the corresponding action. This is the second accepted exception to this feature's general "no parent Android app changes" principle, alongside the manual-pairing-code addition to `ParentPairingActivity` (§3 above) — see `docs/DECISIONS.md`.
- **Injection constraint (flagged, not resolved here)**: Android's `AccessibilityService` API cannot perform true low-level key-event injection — only `dispatchGesture`, `performGlobalAction`, and `AccessibilityNodeInfo` node actions (e.g. `ACTION_SET_TEXT`, `ACTION_SET_SELECTION`, `ACTION_CUT`) are available. This means arrow-key-style cursor movement or Backspace/Enter/Delete/Tab may need to be implemented indirectly — e.g. `ACTION_SET_TEXT` recomputing the focused field's string with an adjusted cursor position/selection, rather than genuine key-event injection. The exact mechanism per key is left to the eventual PLAN.md; this section only flags that the constraint exists so a future PLAN.md is not surprised by it. Escape/Back is the one exception to this constraint — see above.
- **Known limitation: standard text fields only.** As a direct consequence of the injection constraint above, `INPUT_KEY` actions (other than Escape/Back) only function when the parent's currently-focused screen element is a standard Android edit-text-style node the Accessibility API can address. Apps using custom-drawn input surfaces (e.g. games, or apps with Canvas/OpenGL-rendered text fields with no exposed Accessibility node) will not respond to arrow/Backspace/Delete/Enter/Tab key relay — Escape/Back remains the one exception, since `performGlobalAction(GLOBAL_ACTION_BACK)` doesn't depend on node focus at all. This is a known, accepted limitation stemming from a platform constraint, not a defect to fix — Android's Accessibility API provides no lower-level mechanism to work around it.
- **Capture scope: focus-scoped, not global.** `INPUT_KEY` is only sent while the PC client's video-rendering pane has keyboard focus — the ordinary WPF default (key events route to whichever control currently has focus). This is **not** a system-wide/global keyboard hook: keys pressed while any other window or application on the PC has focus are never captured or relayed. This is a deliberate choice to avoid relaying keystrokes typed into unrelated PC windows/apps to the parent's device — see `docs/DECISIONS.md`. Because WPF gives keyboard focus to exactly one control at a time, and `INPUT_KEY` only fires while the video-rendering pane itself holds focus, there is no double-send risk when the operator is instead typing into the separate text-input box (§7): a keypress routes to whichever control currently has focus, never both, so pressing Enter/Backspace while composing an `INPUT_TEXT` message never also fires `INPUT_KEY`.
- Availability: gated behind the same view-only-mode / `ACCESSIBILITY_STATUS` flag as the rest of input (`docs/detailed-spec.md` §11) — `INPUT_KEY` requires the same Accessibility Service permission as `INPUT_TAP`/`INPUT_SWIPE`/`INPUT_TEXT`, so it is disabled together with them, not independently.
- **Implementation hint (not a product decision — a WPF gotcha worth not losing)**: WPF's own default keyboard handling can intercept some of these keys before they reach `INPUT_KEY`'s send logic — e.g. Tab normally triggers WPF's built-in focus-navigation to the next control, and Escape can be intercepted by dialog-close/cancel conventions in some WPF control templates. To ensure these keys are actually captured and relayed rather than consumed by WPF's own default behavior first, the video-rendering pane's key handling should use the `PreviewKeyDown` (tunneling) event and explicitly set `e.Handled = true` after relaying, rather than relying on the bubbling `KeyDown` event alone. This doesn't change any already-decided behavior (which keys are relayed, focus-scoping, Escape→Back mapping) — it's purely a "how to actually make it work in WPF" note for the eventual PLAN.md.

## 12. Known Limitation: Simultaneous Parent-Touch and Remote Input

- Neither this feature nor the existing, already-merged Android app (`docs/spec.md`/`docs/detailed-spec.md`, all tiers) defines what happens if the parent physically touches their own device while the child is remotely sending input (tap/swipe/text/key relay). The two input sources are simply interleaved by Android's normal input pipeline, with no arbitration, locking, or conflict resolution of any kind. This is a **pre-existing gap in the Android app as a whole**, not something newly introduced by the PC client — the PC client does not make this gap any better or worse than it already is for the Android child.
- This is deliberately not solved as part of this feature. Options investigated and why neither was adopted:
  - Automatic real-time arbitration is not achievable without switching the parent's device into Accessibility touch-exploration mode, which would change the parent's entire device interaction model system-wide — unacceptable given this app's target parent user (non-tech-savvy, `docs/spec.md` §2) and its top design priority of minimizing parent-side friction/risk.
  - A manual, child-toggled "lock the parent's touch" overlay is technically feasible but was not adopted for this feature. Competitor research (AnyDesk/TeamViewer-class remote-support tools) confirms this class of tool generally does not offer local-input-locking for Android targets either — only for Windows targets, where `BlockInput()` makes it straightforward. This is a platform capability asymmetry, not a corner cut specifically by this project.
- Tracked as a possible future addition (a manual, child-toggled overlay-based lock, if ever pursued) in GitHub issue [#8](https://github.com/hachi921082-source/Parent-Android-Remote-Control/issues/8) — not scoped or designed further here. See `docs/DECISIONS.md` for the full rationale record.
- **Related, but no longer an open gap: multiple simultaneously-connected clients.** A related question — what happens if a parent is paired to more than one client (e.g. an Android child and this PC client) and more than one attempts to connect at once — was originally going to be left equally undefined here, alongside the touch-arbitration gap above. It has since been decided: see §6's "Exclusive single-session model" bullet, `docs/detailed-spec.md` §17, and `docs/DECISIONS.md` #24. Unlike the touch-arbitration gap above, this is now a fixed, core-app-level rule (only one client may hold an active session at a time), not an accepted open limitation.
