## MediaProjection Resume-After-Process-Kill UX (added 2026-09-03) — RESOLVED 2026-09-03

Background: detailed-spec.md §6 states that after a service kill, "impact is limited to a brief interruption rather than a full session loss requiring the parent to redo the 3-tap (or 2-tap) start flow." On the father's device (MyOS, aggressive background killer per §1), the kind of kill MyOS performs terminates the entire app process, not just a graceful `Service.onDestroy()` while the process itself survives. Android's MediaProjection grant is bound to the process holding it; once that process is killed, the grant is invalidated, and there is no OS API to silently resume screen capture without the parent physically tapping the OS's own "Start Now?" confirmation dialog again — this is a hard platform constraint of the same nature already established in DECISIONS.md #1 (the dialog is unavoidable and, per detailed-spec.md §13 step 2, reappears "every session"). The WorkManager/AlarmManager-based restart that §6 already describes as defense-in-depth can restart the killed process and re-establish the network connection to the child device, but it cannot restore the actual screen-capture grant without that tap — this holds regardless of restart strategy.

So §6's literal wording ("brief interruption... NOT requiring the parent to redo the tap flow") overpromises for the specific MyOS full-process-kill scenario it exists to describe. It is only achievable for lesser cases: a Service stopping while the process itself survives, or a transient network/Tailscale disconnect.

Question: what should actually happen, product-wise, when a full MyOS process-kill occurs mid-session? Three options were identified (raised by developer-lite while drafting the `screen-sharing-core` and `connection-status-and-resilience` PLAN.md files):
- **(A) No special affordance.** After a full-process-kill, sharing has simply stopped; the parent must notice (most likely because the child, already on the call, tells them) and manually re-tap the home-screen widget — the existing 2-tap flow (§4). Simplest, but doesn't literally deliver "brief interruption without redoing the tap flow."
- **(B) Add a "tap to resume sharing" notification.** Triggered by the WorkManager/AlarmManager wake-up (§6) when it detects the process was killed mid-session, a high-priority parent-side notification appears; one tap re-triggers the MediaProjection dialog (still one unavoidable tap per Decision #1). Minimizes the parent's extra steps in this specific failure moment, but introduces a new self-service, parent-facing affordance — a category of design this project has previously leaned away from (see DECISIONS.md #7: an auto-dial-call idea was rejected specifically because the parent's tech proficiency was judged too low to reliably rely on for anything beyond the core minimal flow).
- **(C) Formalize (A) by correcting the spec wording.** Same end-state as (A) — no new UI — but §6's text is corrected to accurately scope the "brief interruption" promise to non-process-death cases only (Service-survives-kill, or a transient network drop), rather than the MyOS full-process-kill case it currently appears to cover.

designer-lite's leaning: (C). It resolves the wording inaccuracy without adding new parent-facing UI, consistent with spec.md §2 ("any design requiring an extra parent-side action beyond the core share-start flow is treated as high-risk") and the precedent set in DECISIONS.md #7 against adding automated/self-service affordances aimed at the parent. That said, this is a leaning, not a decision on the user's behalf — in particular, whether option B's reduced step-count in a real failure moment is worth the added UI/complexity and the deviation from the DECISIONS.md #7 precedent is a product-philosophy call properly left to the user.

Blocks: developer-lite cannot finalize the "service killed mid-session, process died" handling in `docs/plans/screen-sharing-core/PLAN.md` and `docs/plans/connection-status-and-resilience/PLAN.md` — specifically, what the app presents to the parent after such a kill, and whether any new notification/UI component needs to be built for it — until this is resolved. `detailed-spec.md` §6's wording is left as-is until the user decides, since editing it now (even just to narrow its scope) would itself bake in a provisional choice among A/B/C.

**Resolution**: user chose (C) — no dedicated recovery UI; `detailed-spec.md` §6's wording has been corrected to scope the "brief interruption" promise to process-survives/transient-network cases only. See `docs/DECISIONS.md` #13. developer-lite may now finalize the two blocked PLAN.md sub-items using option (C)/(A)'s end-state (no new notification/UI component for this case).

## UI Language / Locale Support (added 2026-09-03) — RESOLVED 2026-09-03

Background: A gap was found during review — UI language/locale is never specified anywhere in `spec.md`/`detailed-spec.md`, despite the target users being non-tech-savvy parents (spec.md §2) on Japanese-market devices (AQUOS Wish4, ZTE Nubia S2, detailed-spec.md §1). detailed-spec.md §5, §11, §14, §17 each state that UI "wording" is "left to implementation/PLAN.md" — this silently included the language itself, not just phrasing/styling, and the already-implemented and merged Tier 0 (Pairing & Onboarding) feature ended up with 100%-English `strings.xml` as a direct consequence (flagged as a non-blocking observation in that feature's reviewer-lite pass, recorded in `docs/HANDOFF.md`).

Question: which language(s) should the app's UI support, and how should the language be selected (manual in-app picker vs. automatic system-locale detection)?

**Resolution**: user decided directly (this was raised to and discussed with the user outside the numbered-options flow used for other QA.md items above):
- Supported languages: Japanese, English, and Chinese (ja/en/zh) — applies to all UI text across both parent-facing and child-facing screens, for the whole app (not scoped to onboarding only).
- Selection mechanism: automatic, following the device's OS system locale (standard Android resource-qualifier mechanism — `values-ja/strings.xml`, `values-zh/strings.xml`, default `values/strings.xml`). No in-app manual language picker/switcher — consistent with spec.md §2's top design priority of minimizing parent-side steps: a manual picker would add a setup step, whereas system-locale auto-detection adds zero.
- Fallback: for any system locale other than ja/en/zh (e.g. Korean), fall back to English — this is the Android-standard default-resource behavior (the unqualified `values/strings.xml`, authored in English, serves as the fallback for any unmatched locale), not a special case requiring extra logic.

See `docs/DECISIONS.md` #14 for rationale. `docs/spec.md` §6 and `docs/detailed-spec.md` §18 have been updated accordingly; `docs/detailed-spec.md` §5, §11, §14, §17 now cross-reference §18 to clarify that their "wording left to implementation" bullets no longer imply English-only.

## PC Viewer Client: Does the ja/en/zh UI-Language Policy Apply to Its UI Too? (added 2026-09-03) — RESOLVED 2026-09-03

Background: the existing Android app's UI-language policy (`docs/detailed-spec.md` §18, `docs/DECISIONS.md` #14) supports Japanese, English, and Chinese across "every user-facing string resource in the app — both parent-facing and child-facing screens," selected automatically from the device's OS system locale, with no in-app manual picker. The new Windows PC viewer/controller client (`docs/pc-client-spec.md`, `docs/pc-client-detailed-spec.md`) introduces a second, separate UI (WPF, its own resource/localization mechanism, e.g. `.resx` files keyed by `CultureInfo.CurrentUICulture`) that this existing policy was never written with in mind.

There are reasonable arguments on both sides:
- **For applying the same policy**: this project already has an established, family-facing ja/en/zh posture across every existing screen (parent and child alike, per `docs/detailed-spec.md` §18's "not just the onboarding flow" language); the PC client's operator is the same child role already covered by that policy, and a Windows equivalent (`.resx` + `CultureInfo.CurrentUICulture` fallback) is mechanically straightforward to mirror.
- **Against, or for a narrower scope**: the PC client is operated only by the tech-comfortable child (never by a non-tech-savvy parent, unlike the Android app where §2's "minimize parent-side friction" was a large part of why auto-detection over a manual picker was chosen in the first place) — the driving rationale behind ja/en/zh support for the Android app was partly about non-tech-savvy parent-facing screens, which this PC client has none of. Building and maintaining three-language resource sets for a brand-new codebase is also nonzero ongoing cost, which the user may or may not want to take on immediately for a new client that ships with just one operator role.

Question: should the PC client's UI support Japanese, English, and Chinese (auto-detected from the Windows OS locale, same as the Android app), or should it launch English-only (or with some other language scope), at least initially?

Blocks: `docs/pc-client-detailed-spec.md` §9 is left explicitly open pending this answer; a future PLAN.md for this feature cannot finalize its localization/resource-file structure until this is resolved.

**Resolution**: user confirmed directly — yes, the PC client's UI supports Japanese, English, and Chinese (ja/en/zh), same as the Android app: automatic selection from the OS locale, English fallback, no in-app manual picker. `docs/pc-client-detailed-spec.md` §9 and `docs/pc-client-spec.md` §5 have been updated accordingly (WPF `.resx` resources keyed by `CultureInfo.CurrentUICulture` as the implementation vehicle). No new `docs/DECISIONS.md` entry was needed for this one — it is a direct extension of the already-decided policy (`docs/DECISIONS.md` #14), not a new comparative decision.

## Exclusive Single-Session Model (added 2026-09-03) — RESOLVED 2026-09-03

Background: `docs/plans/screen-sharing-core/PLAN.md` §6 (already merged, Tier 1) has the parent dial **all** known `AuthorizedChild` records simultaneously at share-start time, each independently becoming a live peer with full equal tap/swipe/text control — explicitly called out at the time as undefined/unarbitrated behavior ("out of scope to design a 'which child is actively waiting' negotiation beyond attempting all known children, since spec.md only anticipates a single child device in practice"). This was revisited during PC Viewer Client planning: the new PC client makes a parent being simultaneously connected to more than one client (e.g. an Android child **and** the PC client, or two Android children) a real, practically-reachable scenario rather than a purely theoretical one, since it's now common for the same parent to be paired to both an Android child and a PC client at once.

Question: when a parent is paired to more than one client device, should all of them be allowed to hold simultaneous, independent, fully-equal `Live` control sessions (the original, undefined-conflict behavior), or should only one client be allowed an active session at a time?

**Resolution**: user decided — **exclusive single-session model**. Only one client (Android child or PC client, any type) may be in an active `Live` session with a given parent device at a time. If a session is already active and another paired client attempts to connect, that attempt is rejected or queued rather than accepted as a second concurrent peer. The exact rejection mechanism (silent drop vs. an explicit "busy" response vs. queue-and-connect-after) is left open as a PLAN.md/implementation-level detail — only the exclusivity requirement itself is fixed here. See `docs/DECISIONS.md` #24 for the rationale. `docs/detailed-spec.md` §17 and `docs/spec.md` §5 have been updated accordingly; `docs/pc-client-detailed-spec.md` §6 has been updated to state the PC client is simply one more client type subject to this same rule. Actual code-level implementation of this rule in `docs/plans/screen-sharing-core/PLAN.md` and `docs/plans/connection-status-and-resilience/PLAN.md` (both already merged, Tier 1/2) is tracked as a follow-up in GitHub issue [#9](https://github.com/hachi921082-source/Parent-Android-Remote-Control/issues/9), not implemented in this session.

## Single-Session Rejection Mechanism (added 2026-09-03) — RESOLVED 2026-09-03

Background: the "Exclusive Single-Session Model" entry above fixed the exclusivity requirement itself but explicitly left open what the losing (second-arriving) client experiences. `docs/plans/single-session-enforcement/PLAN.md` §4 (the implementation plan for GitHub issue #9) laid out four concrete options as two independent axes — give the loser explicit notice or not, and let it retry automatically or not — and flagged this as a genuine product-facing UX decision rather than resolving it silently.

Question: when a client loses the parent-side arbitration race (another client already holds the active session), what does that losing client see/do — nothing at all (silent drop), nothing but an automatic retry within the existing reconnect window (silent + retry), an explicit "another device is connected" screen with no further retry (explicit + give up), or an explicit notice that still retries automatically (explicit + retry, the least-specified option)?

**Resolution**: user decided — **explicit "busy" notice, then give up (terminal)**. The losing client is told, immediately and explicitly, that another device is already connected, and its connection attempt ends there — it does not automatically retry; the user must act again once the other session ends. This is the option `docs/plans/single-session-enforcement/PLAN.md` §4 identified as most informative to a non-tech-savvy user and consistent with this project's existing terminal-state UI pattern (`Disconnected`). Implementation per that plan's §5 (new `SESSION_BUSY` wire message) and §6 (new `ConnectionState.Rejected`, new `session_rejected_title` string in ja/en/zh) can now proceed — no longer blocked on this decision. Note: §5 adds a new `net/MessageType.kt` enum value, the same file `docs/plans/pc-key-relay-support/PLAN.md` (in progress in a separate worktree as of this resolution) also edits to add `INPUT_KEY` — these two should not be implemented in unmerged parallel worktrees at the same time; sequence them (whichever merges first picks the next free tag) rather than risking a same-file conflict.
