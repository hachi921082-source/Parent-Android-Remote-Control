## 1. Scope

Everything needed for the PC client to acquire and manage its own list of paired parent devices: the manual two-field pairing screen, the handshake that turns a typed host+code into a stored `PcPairingEntry`, and basic list management (rename/delete). Does not cover session establishment against an already-paired parent (that's `docs/plans/pc-client/video-and-session/connectivity.PLAN.md`) or which screen is shown on launch (that's `docs/plans/pc-client/connection-state-ui/PLAN.md` §4) — this plan owns the pairing data and the pairing-acquisition screen only.

## 2. Data Model

Namespace: `FamilyRemote.PcClient.Pairing`.

```csharp
public record PcPairingEntry(
    Guid Id,             // = pairingId, from the parent's PAIRING_ACK
    string Label,         // free-form, editable any time (docs/spec.md §5)
    string ParentHost,     // parent's Tailscale IP or MagicDNS name, operator-typed
    string SharedSecret,   // random 256-bit token, base64url, generated by this client
    DateTimeOffset CreatedAt
);
```

Directly mirrors the Android child's `PairingEntry` (`docs/plans/pairing-and-onboarding/PLAN.md` §2.1) field-for-field, per `docs/pc-client-detailed-spec.md` §4's explicit confirmation that this is needed — a separate, PC-local list, independent of any Android child's own list (same parent device paired to both gets two independent entries with two independent shared secrets).

`Label` is mutable (`with { Label = newLabel }` on record `PcPairingEntry`, or a plain settable property if a class is used instead of a record — implementation choice, record chosen here since the type is otherwise immutable and small).

## 3. Storage

- File: `%LOCALAPPDATA%\FamilyRemote.PcClient\pairing_entries.json` — a JSON array of `PcPairingEntry`, serialized via `System.Text.Json`.
- At-rest protection: the serialized JSON bytes are encrypted via Windows Data Protection API (`System.Security.Cryptography.ProtectedData.Protect(bytes, optionalEntropy: null, DataProtectionScope.CurrentUser)`) before being written to disk, and decrypted on read. Chosen as a lightweight parity measure with the Android app's `EncryptedSharedPreferences` choice (`docs/plans/pairing-and-onboarding/PLAN.md` §2.1) — DPAPI is a built-in OS API (no third-party dependency, consistent with `docs/DECISIONS.md` #16's general preference for OS-native mechanisms over pulled-in libraries), and ties the encrypted blob to the current Windows user account, which is an appropriate-strength match for this app's minimal-security, family-only posture (`docs/spec.md` §7) — not a hardened secrets-vault requirement.
- `PcPairingRepository` class: `IReadOnlyList<PcPairingEntry> GetAll()`, `void Add(PcPairingEntry entry)`, `void UpdateLabel(Guid id, string newLabel)`, `void Delete(Guid id)` — same method shape as the Android `PairingRepository`'s child-side half (`docs/plans/pairing-and-onboarding/PLAN.md` §3), read-modify-write the whole list on every mutation (dataset is tiny, no need for incremental update logic).

## 4. Crockford Base32 Normalization

Namespace: `FamilyRemote.PcClient.Pairing` (or `Common`, since it's a small pure-function helper with no PC-pairing-specific state — implementation choice, placed in `Pairing` here since it has no other caller).

```csharp
public static class CrockfordBase32
{
    // Per pc-client-detailed-spec.md §3: strip separators, uppercase, then alias-correct
    // I/L -> 1, O -> 0. No mapping exists for 'U' -- Crockford's standard simply excludes it
    // from the alphabet rather than aliasing it, so a stray typed 'U' passes through unchanged
    // and will not match any valid generated code (expected/acceptable).
    public static string Normalize(string input)
    {
        var stripped = input.Trim().Replace("-", "").Replace(" ", "").ToUpperInvariant();
        var sb = new StringBuilder(stripped.Length);
        foreach (var c in stripped)
        {
            sb.Append(c switch
            {
                'I' or 'L' => '1',
                'O' => '0',
                _ => c
            });
        }
        return sb.ToString();
    }
}
```

The operator-typed host address field is not run through this normalization — only the code field is (the parent's displayed code may be grouped with dashes for readability per `docs/pc-client-detailed-spec.md` §3's "exact text rendering... left open" note, so this client must tolerate either grouped or ungrouped display; a Tailscale host address/hostname has no analogous grouping convention to strip).

- After normalization, the result must be exactly 8 characters and use only the Crockford alphabet (`docs/plans/pc-client/README.md` §6's `CrockfordAlphabet` constant) for the "Pair" button to be enabled — a client-side format pre-check, purely a UX nicety (catches an obviously-mistyped code before a wasted network round-trip); the parent remains the sole authority on whether the code actually matches (§6 below).

## 5. Manual Pairing Screen (Two-Field UI)

Per `docs/pc-client-spec.md` §6 / `docs/pc-client-detailed-spec.md` §3:

- `Pairing/ManualPairingView.xaml` (a `UserControl` or `Window`, hosted by `connection-state-ui`'s content root per `docs/plans/pc-client/app-shell/PLAN.md` §2): two `TextBox` fields — host address (free-text, no format validation beyond non-empty, since Tailscale hostnames/IPs have no single validatable shape worth enforcing here) and manual code (8-char, format-checked live per §4's note) — plus a "Pair" button (enabled only once both fields are non-empty and the code passes the format pre-check) and a status/error text area.
- On submit: normalize the code (§4), then run the handshake (§6). While in flight, the "Pair" button is disabled and a "Connecting…" status is shown (mirrors the Android `ParentPairingActivity`'s status-text pattern, `app/src/main/java/com/familyremote/app/pairing/ParentPairingActivity.kt`).
- On handshake success: prompt for a label (a simple second `TextBox` dialog/step, "Name this device", pre-filled suggestion "Parent" — mirrors `PairingLabelPromptActivity`'s Android equivalent), then save via `PcPairingRepository.Add` and hand off to `docs/plans/pc-client/connection-state-ui/PLAN.md`'s `WaitingForParent` flow for the newly-created entry.
- On failure (timeout, network error, code/host mismatch — the parent gives no distinct "wrong code" vs. "wrong host" signal, since a TCP connection to a wrong host address simply fails/times out and a wrong code is indistinguishable from any other unauthenticated attempt per the Android-side design, `docs/plans/pc-pairing-code-support/PLAN.md`): show a generic retry-capable error message and re-enable the form — no attempt-count UI on this side (the lockout, per `docs/pc-client-detailed-spec.md` §3, is enforced parent-side, not client-side; the PC client has no way to know it happened except by its own attempts eventually stopping succeeding, which surfaces as the same generic error).

## 6. Pairing Handshake (PC as Initiator)

Per `docs/pc-client-detailed-spec.md` §3's last bullet — identical steps to `docs/plans/pairing-and-onboarding/PLAN.md` §4 steps 3-5 (the Android `ChildPairingScanActivity`'s role), just starting from typed input instead of a scanned QR:

1. Resolve this PC's own Tailscale address via `PcTailscaleAddressResolver` (§8 below — needed as the `childHost` value the parent stores).
2. Open a TCP connection to `{operator-typed host}:PairingPort` (`Common.Constants.PairingPort = 47322`).
3. Send a `PAIRING_HELLO` frame (`Net.MessageType.PairingHello`, same wire shape as the Android `PairingHelloPayload`, `app/src/main/java/com/familyremote/app/pairing/PairingHandshakeMessages.kt`): `{tempToken: <normalized 8-char code>, childHost: <resolved PC Tailscale address>, proposedSecret: <freshly generated 256-bit token>}`. The JSON field name stays `tempToken` even though this client's value is the manual code, not a QR token — the parent-side listener (`docs/plans/pc-pairing-code-support/PLAN.md`) inspects the value's shape (8-char Crockford-alphabet string vs. a longer base64url token) to decide which credential it's being checked against; no new field/message shape is introduced (`docs/pc-client-detailed-spec.md` §3 does not ask for one).
4. On receiving `PAIRING_ACK {childId}` before the 5-minute window elapses: proceed to the label prompt (§5) with `Id = childId`, `ParentHost = {operator-typed host}`, `SharedSecret = proposedSecret`.
5. On timeout, connection refusal, or the socket closing without an ack (parent-side mismatch/lockout, per `docs/plans/pc-pairing-code-support/PLAN.md` §4's silent-close-on-failure design): surface the generic retry error (§5).
6. `Net.SharedSecret` generation: 32 random bytes from `RandomNumberGenerator.Fill`, base64url-encoded (`Convert.ToBase64String` with `+`/`/` replaced by `-`/`_` and padding stripped) — matches the Android app's `SecureTokenGenerator.generateSharedSecret()` encoding exactly (`app/src/main/java/com/familyremote/app/pairing/SecureTokenGenerator.kt`), since this value round-trips through the parent's own storage and must be byte-for-byte comparable later at session-establishment time.

## 7. Pairing List / Rename / Delete

- `Pairing/PairingListView.xaml`: lists existing `PcPairingEntry` rows (label + host, a rename affordance, a delete affordance, and "Add new pairing" which opens `ManualPairingView`, §5) — shown only when 2+ entries exist per `docs/plans/pc-client/connection-state-ui/PLAN.md` §4's selection-flow rules; also reachable at any time as a management screen (mirrors the Android `PairingListActivity`/`PairingListFragment`'s dual role).
- Rename: inline edit or a small dialog → `PcPairingRepository.UpdateLabel` → persists immediately. Never touches `ParentHost`/`SharedSecret`/`Id`, never contacts the parent (`docs/spec.md` §5 / `docs/detailed-spec.md` §3 — same rule as the Android app, ported directly).
- Delete: `PcPairingRepository.Delete` → persists immediately, no confirmation-dialog requirement specified (an implementation-level UX nicety left open, same as it was for the Android app).

## 8. Interactions With Other Features

- **app-shell**: hosted inside `MainWindow`'s content root; consumes `Resources.Strings` for all text and `Common.Constants` for `PairingPort`/`PairingCodeValidityMs`.
- **connection-state-ui**: that plan drives *which* screen (this plan's `ManualPairingView`/`PairingListView`, or a `WaitingForParent` screen) is shown on launch and after a pairing completes — this plan only owns the screens themselves and the data they operate on, not the launch-time routing logic.
- **video-and-session/connectivity**: reuses this plan's `PcTailscaleAddressResolver` (a small standalone class, `Pairing/PcTailscaleAddressResolver.cs` — enumerates `NetworkInterface.GetAllNetworkInterfaces()`, selects the first IPv4 unicast address in `100.64.0.0/10`, mirrors `docs/plans/pairing-and-onboarding/PLAN.md` §3's `TailscaleAddressResolver` logic exactly) for its own connectivity checks, rather than duplicating Tailscale-detection logic.
- **docs/plans/pc-pairing-code-support/PLAN.md (Android side)**: that plan's `PairingServer` redesign is the exact server-side counterpart this section's handshake talks to — the two plans must stay in sync on the `PAIRING_HELLO`/`PAIRING_ACK` wire shape and the "8-char Crockford-alphabet string vs. longer token" disambiguation rule (§6 point 3 above); do not let either plan's field names or matching logic drift without updating the other.

## 9. Open Items

None. `docs/pc-client-detailed-spec.md` §3/§4 fix every product-level requirement this plan needs; the remaining choices (exact storage format, DPAPI use, second-dialog label prompt UX, delete-confirmation) are implementation-level and resolved directly above, consistent with how the equivalent Android plan (`docs/plans/pairing-and-onboarding/PLAN.md` §8.1/§8.2) resolved its own analogous gaps without escalation.
