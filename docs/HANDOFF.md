## 1c. New session (2026-09-05) — issue #30 root-caused and fixed; 4 more real-device bugs found and fixed; 3 new gaps found, still open

Picked up exactly where §1b left off, with sense8, a second AQUOS sense4 (also borrowed for this session, serial `354961113255363`, SoC Qualcomm SM7125/Snapdragon 662), and M06 all simultaneously available. **All work described here is committed and pushed to `origin/master`** (`4317dd8`..`d1396a7`, 11 commits, no feature branch -- done as direct small fixes per this project's existing precedent for small/well-understood changes, not through developer-lite/reviewer-lite). Issues #30/#31/#32/#33/#36 are closed; #34/#35/#37 remain open (see §4).

- **Issue #30 root cause found**: sense8's hardware AVC encoder (`c2.qti.avc.encoder`, Qualcomm's Codec2/V4L2 HAL) logs `OPAQUE is not a supported pixel format!` and silently produces a solid-black stream when fed via the app's `COLOR_FormatSurface` (zero-copy Surface-input) encoder configuration -- no exception, no callback, nothing visible anywhere. Confirmed this is a config-specific bug, not a hardware limitation, by installing AnyDesk on sense8 and confirming it *can* correctly stream that same device's own screen to a PC -- AnyDesk turned out to not use the OS's hardware `MediaCodec` pipeline at all, instead shipping its own proprietary software codec (DeskRT) precisely to avoid this whole class of OEM encoder bug.
  - **Confirmed on 3 separate real Qualcomm chips/driver generations, not just sense8**: sense4 (older SM7125, legacy `OMX.qcom.video.encoder.avc` HAL) shows an analogous `C2DColorConvert: calcYSize: Format not supported` warning; **M06 itself** (SM7435, previously only ever used as the *receiving* child in every earlier test) shows the exact same `OPAQUE is not a supported pixel format!` message as sense8 when put in the *parent/sending* role -- ruling out "maybe it's the receiver's decoder, not the sender's encoder" (a real alternative hypothesis the user raised and that got checked properly, not assumed away).
  - **Explicit correction on the record, don't re-claim otherwise without new evidence**: this session initially over-stated "Qualcomm-specific, so the real target devices (AQUOS Wish4 = MediaTek Dimensity 700, ZTE Nubia S2 = Unisoc) are safe" -- that is **not proven**, only that this *specific* Qualcomm-branded error signature won't literally reproduce on a different vendor's completely separate HAL implementation. Wish4/Nubia S2 have never been tested (they're the parents' actual daily-use devices, not available to borrow for testing) and could in principle have their own unrelated Surface-input quirk. Treat as "unverified", not "confirmed safe", until someone actually tests on one.
  - **Fix**: `ScreenCaptureEncoder` rewritten from Surface-input to buffer-input (`ImageReader` captures RGBA, converted in software to YUV420 in `convertRgbaToI420`, fed via `MediaCodec.getInputImage()`). Still hardware-accelerated for the actual H.264 compression step -- only the color-space conversion is now software, not a full custom software codec like AnyDesk's. **Confirmed working end-to-end on real hardware**: M06→sense4 live video, stable, no black screen, first time this project has ever had a genuinely working screen-share between two independent real devices.
  - Two more real crashes were found and fixed *while getting the above working* (both device-independent, not Qualcomm-specific):
    - **Issue #32**: `ScreenShareForegroundService.handleNoValidGrantAtStart()` called `startForeground()` on a `foregroundServiceType="mediaProjection"`-declared service with no actual grant -- on API 34+ this always throws `SecurityException` regardless of the notification content. Fixed by not calling `startForeground()` at all on that path, just `stopSelf()`.
    - **Issue #33**: `onNalUnit`'s callback (already strictly sequential -- `MediaCodec.Callback` delivers one at a time on its own thread) was re-wrapped in a fresh `serviceScope.launch(Dispatchers.IO) { ... }` per NAL unit, losing that ordering guarantee; concurrent writes to the same child's socket could interleave mid-write and corrupt the `MessageFrame` length-prefix framing, crashing the child with `IllegalArgumentException: Invalid frame length`. Fixed with a single ordered `Channel`-backed consumer in `ScreenShareForegroundService`. **This alone was not sufficient** -- `ParentSessionServer.sendSessionEndAndClose()` writes to the same socket via a completely separate code path (bypassing the ordered queue entirely), so the exact same crash reproduced the first time the new stop-sharing button (see #36 below) was exercised. Real fix: a `Mutex` inside `ParentSessionServer` guarding *every* write path (`sendFrame`/`sendVideoFrame`/`sendSessionEndAndClose`), not just the video-frame one. Lesson for next time this class of bug shows up: find and lock the single shared resource (the socket), don't chase each call site that happens to write to it one at a time.
- **Issue #31 fixed**: there was no way to delete a stale/duplicate `AuthorizedChild` entry short of `pm clear`-ing the whole app (a real, previously-undocumented gap -- an earlier handoff's claim that this was possible "via the pairing list UI" was checked this session and found to be wrong; that UI shows a different, unrelated list). New `AuthorizedChildListActivity` (reachable from the parent home screen's new "Manage Viewers" button) lists and deletes them.
- **Issue #36 fixed**: there was genuinely no way to explicitly stop a share session from within the app -- `ACTION_STOP`/`createStopIntent()` existed in code but nothing ever called them; only the OS's own generic MediaProjection "stop casting" control worked. Added a notification action button and turned the parent home screen's "Show Screen" button into a start/stop toggle (driven by `ScreenShareForegroundService.isRunning`) rather than adding a second button, to keep that screen at its existing one-primary-action size for the elderly-parent audience.
- **Two more real-device findings, not yet fixed, filed as issues #34/#35/#37 (see §4)**.
- **Process notes worth keeping for next time** (also written to this session's memory):
  - When the user names a specific competing app that works where this app doesn't, research *how* that app actually does it (web search is enough) before writing a fix -- this session implemented and tested a narrower "swap to a different named hardware encoder" fix first, which then failed because the device in question has no alternative hardware encoder at all; only afterward did research surface that the competitor doesn't use the OS hardware pipeline at all. The user was right to call this out as something that should've been checked first.
  - Every real device this session touched (sense8, sense4, M06) turned out to be Qualcomm -- don't casually assume "tested on real hardware" generalizes across SoC vendors without checking `getprop | grep soc` first.
