- **Background on the resolved item** (kept for record): `docs/plans/pc-pairing-code-support/PLAN.md`'s `PairingServer` redesign changes behavior of the **already-merged, already-shipped** QR-only Android-to-Android pairing flow as a side effect. Previously (as merged) `PairingServer` accepted exactly one connection attempt and closed regardless of outcome (see its own doc comment). `docs/pc-client-detailed-spec.md` §3 requires the manual pairing code and the QR's `tempToken` to share the same temporary listener with independent lockout counters; PLAN.md §4 implements this by having the shared listener tolerate up to 5 failed attempts (per channel, tracked independently) before that channel locks out for the remainder of the 5-minute window, instead of closing on the very first failure — this applies uniformly, so a bad QR attempt is now also tolerated up to the same bound rather than closing the listener immediately. This was spec-mandated and explicitly reasoned about inline (reviewer-lite confirmed it's flagged, not a silent decision). Option considered and rejected: fully separating QR/manual-code failure handling (QR keeps closing immediately on any failure, only the manual-code channel tolerates retries) — technically feasible via shape-based disambiguation of the incoming credential, but adds implementation complexity for a security difference judged negligible given the app's family-only threat model (`docs/spec.md` §7). User confirmed proceeding with the simpler, already-written PLAN.md design.

## PC Viewer Client — what's decided (summary; read `docs/pc-client-spec.md`/`docs/pc-client-detailed-spec.md` for full detail, and the 11 PLAN.md files for implementation-level detail)

- Additional client type alongside the Android child app (not a replacement); Windows-only, Windows 10+; C#/.NET, WPF; single portable exe, no installer; single-instance-enforced (named mutex); ordinary window app (no tray/background, no pause-on-minimize).
- Video: parent's Android app is completely unchanged — reuses the existing H.264 wire protocol as-is; PC client decodes via Windows Media Foundation (not FFmpeg — licensing), low-latency configured (`CODECAPI_AVLowLatencyMode` or equivalent).
- Pairing: `ParentPairingActivity` gains a small addition — shows a plain-text host address plus a new 8-character Crockford Base32 manual code (I/L/O/U excluded, case-insensitive with full alias correction, independent rate-limit counter from the QR `tempToken`'s, threshold=5) alongside the existing QR. This plus the key-relay addition below are the only two Android-side code changes this feature needs.
- New features beyond parity with the Android child: zoom/magnifier (mouse-wheel, capped to fit window, dynamically re-clamped on resize, no pan needed), physical key relay (new `INPUT_KEY` wire message, now in `docs/plans/README.md` §4's shared protocol table; arrows/Backspace/Delete/Enter/Tab/Escape; Escape→`GLOBAL_ACTION_BACK`; focus-scoped capture via WPF `PreviewKeyDown`, not global).
- Deliberately deferred (`docs/pc-client-spec.md` §10 Future Extensions): multi-parent-tabs, PC→parent file transfer, manual touch-lock overlay (issue #8).
- Everything else (connection states/timeouts, tap-marker behavior, view-only mode, status summary, rotation handling, coordinate scaling, pairing-selection-on-launch flow, post-Disconnected destination) reuses the Android child's existing behavior/wire protocol unchanged.
